# Changelog

All notable changes to the `agent-coherence` Claude Code plugin are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions adhere to [SemVer 2.0](https://semver.org/spec/v2.0.0.html).

Alpha — APIs and the `hooks.json` wire shape may change before `v1.0`.

The canonical release-notes surface is [GitHub Releases](https://github.com/Cohexa-ai/agent-coherence-plugin/releases); this file mirrors that history in a structured format for operators who prefer a single browsable timeline.

## [Unreleased]

### Added

- **A check that reports when `dev`'s lockfile falls behind `main`'s, on a daily schedule and on pushes to `main` and `dev`.** Dependabot builds its dependency graph from the **default branch only** — `.github/dependabot.yml` says so in its own comment — so a security advisory produces exactly one alert and one PR, both scoped to `main`, and `dev` is never examined even though every feature branch is cut from it. That makes the `main` → `dev` forward-merge half of the remediation, and it is the half with no alert behind it. The record is unambiguous: alert #5 (js-yaml, 2026-08-23) recorded `fixed_at` **four seconds** after PR [#102](https://github.com/Cohexa-ai/agent-coherence-plugin/pull/102) merged to `main` and **forty-one minutes before** PR [#109](https://github.com/Cohexa-ai/agent-coherence-plugin/pull/109) carried the same bump to `dev`; alert #6, the same package again, closed **five seconds** after PR [#128](https://github.com/Cohexa-ai/agent-coherence-plugin/pull/128) merged while `dev` still sat on 4.3.1. Between them twelve main-only commits accumulated with no forward-merge, every one authored by `dependabot[bot]`. `tools/check_lockfile_drift.js` runs from a new `lockfile-drift` workflow. Its trigger list needs stating precisely, because the obvious reading is wrong twice. A push-triggered workflow resolves its definition from the ref that was pushed, so the `main` half of the trigger matches nothing until the workflow file is itself on `main`, and arms at the release that carries it over; the `dev` half is live immediately, which is what covers a forward-merge landing. More importantly, **a push made with `GITHUB_TOKEN` creates no workflow run at all** — GitHub suppresses it so workflows cannot trigger themselves — and `dependabot-automerge.yml` merges with exactly that token. Measured on `main`, twelve of the last thirteen pushes produced zero runs from *any* workflow; the three Monday auto-merge batches (2026-08-31, 09-07, 09-14, four commits each) fired nothing, while the human-merged pushes on 08-23, 08-25 and 09-16 each fired. The guard's purpose survives that only because `dependabot-automerge.yml` excludes production dependencies and majors, so a security advisory always waits for a human and a human merge does fire — PR #128 above is that case. The **daily schedule** is therefore the trigger that actually carries the guard: a cron run is not a push, so no suppression applies, and because the comparison reads the two branch tips rather than a pushed commit, one run reports every drift accumulated since the last regardless of who merged what. Like the `main` push trigger it runs only from the default branch, so it arms at the same release. `workflow_dispatch` works against any ref that carries the file. A red check is visible and blocks nothing. It is deliberately **not** part of the release preflight: a release tag points at `main`, so `dev`'s state says nothing about whether the artifact being tagged is correct, and gating the tag on it would block a good release for an unrelated condition at the one moment it cannot be retried, since the `refs/tags/v*` ruleset forbids deletion and non-fast-forward. The comparison is a standalone pure module, `tools/lockfile_drift.js`, which imports nothing; `tools/check_release_readiness.js` keeps only the thin `gh`-fetching wrapper, so the dependency runs from the preflight toward the library rather than the reverse, and `src/test/lockfile_drift.test.ts` exercises the rules with no network round-trip. It is keyed on `name@major` **lineage**, collapsing each side to the **lowest and highest** version in that lineage. Not by lockfile path, because npm hoists a package between `node_modules/x` and `node_modules/dep/node_modules/x`, so a path key misses `dev` holding a vulnerable copy nested under a dependency. Not by bare **name** either: one name is routinely installed at two lineages at once — this repo has `ignore` at 5.3.2 and 7.0.5, and `eslint-visitor-keys` at 3.4.3 and 5.0.1 across four paths — which collapses both branches to the same shared minimum and hides a bump to the higher lineage entirely. And not by the lowest alone: that is right on the `dev` side, where it catches a branch carrying both the patched and the vulnerable copy, but it **inverts** on the `main` side, where a `main` holding two same-major copies collapses to the older one and a `dev` sitting at exactly that version compares equal and is certified clean — the precise alert shape the check exists for, reported as healthy. Tracking both ends fixes that, because "is `dev` behind" is an interval question: `dev` is behind when its lowest is under `main`'s lowest, or its highest is under `main`'s highest. A `main` lineage with no `dev` counterpart falls back to `dev`'s highest lower major, so a bump crossing a major boundary is caught rather than skipped: of the twenty packages found on the first live run, three (`file-entry-cache` 8→11, `flat-cache` 4→6, `keyv` 4→5) were major bumps that a lineage key without that fallback would have dropped silently. A lineage `dev` carries and `main` does not is `dev`'s own dependency tree, not a missed forward-merge, and is not flagged. An unreadable or structurally empty lockfile **fails** rather than certifying; HTTP 403 stays a warning in the level, because it is about the token rather than the lockfiles, but it still exits non-zero — a run that compared nothing must not paint a green check indistinguishable from a real pass. The closing line is keyed on *why* the run is not a pass, so only a proven drift ever tells an operator that `dev` is missing an update. And when every older copy is nested under one of `dev`'s own dependencies the verdict drops the forward-merge instruction, because that merge cannot change `dev`'s transitive tree.

### Changed

- **`/status` no longer publishes a raw session identifier.** Each session row
  carried `agent_name` as `claude-session-<session id>`, beside the
  non-reversible `agent_id`. This coordinator serves no `detail=full` tier, so
  the tier rendering it was the only tier it has; `agent_name` is now `null`,
  and `agent_id` and the per-artifact states are unchanged. In
  `agent-coherence` releases after 0.14.1, the Python coordinator redacts the
  same field below its operator tier, so both backends now return `null` for
  `agent_name` below the operator tier.

- **A hook response names a peer by agent id, and a denial no longer reports a
  write that did not happen.** The last-writer field on stale responses and
  strict denies carried a peer's raw session id, reversed out of the agent id
  by a lookup that has been removed rather than left unused. A denial issued
  when a peer merely took the grant also claimed the artifact "was updated",
  naming a timestamp for a write that never occurred; that case now has its
  own message. Both texts are byte-identical to the Python coordinator's in
  `agent-coherence` releases after 0.14.1.

### Fixed

- **A policy file with long runs of blank lines no longer stalls the coordinator on every track or untrack.** The writer trimmed the file's trailing newlines with a `/\n+$/` replace, which backtracks over every run of newlines in the file and is quadratic in its length: 60,000 blank lines inside a list (well under the 64 KB cap) blocked the coordinator's only event loop for about 2.3 seconds per call. The trim is now a linear scan with the same result, 5 ms on the same file.

- **Tracking or untracking a pattern that starts with `*` no longer silently drops every other entry in the file** ([#178](https://github.com/Cohexa-ai/agent-coherence-plugin/issues/178)). `/policy/track` and `/policy/untrack` wrote each entry to `tracked.yaml` / `ignored.yaml` as a YAML plain scalar, `- ${p}`, and a plain scalar is not literal. A leading `*` is an alias, so untracking `*.log` stopped `ignored.yaml` parsing; the loader then fell back to no entries, every earlier ignore stopped applying, and the request still answered success. Several other leading characters (`!` `[` `{` `|` `%` `@` `` ` `` and quotes) break the file the same way; `&`, `#`, `key: value` and values such as `null`, `123` or `true` silently drop the one entry; and ` #` mid-path quietly turned `docs/x #1.md` into the pattern `docs/x`. Entries are now written as double-quoted scalars through js-yaml's own dumper, so every one reads back as exactly the string that was sent. The dumper rather than `JSON.stringify` because both backends read these files, and PyYAML folds a raw NEL (U+0085, which path validation admits) inside a quoted scalar to a space; the dumper writes it as `\N`. For every ASCII path the bytes match what `json.dumps` produces, which is the fix proposed for the Python writer's identical defect (Cohexa-ai/agent-coherence#284). Existing lines are left as they are. The writer now also refuses, writing nothing and answering 400, whenever an append could not take effect: a file an earlier unquoted write already broke (it loads as no entries, so the new entry never would either), a file that holds something other than a list, a valid list in a layout an appended line would break (a `[ ... ]` list, an indented list or a `...` end marker, where the write used to erase entries that were working), and a file it cannot read (which it used to treat as empty and replace with only the new entries). The message names the file, says where the parser stopped, and says how to rewrite it. The Node `agent-coherence-track` / `-untrack` CLIs now print that message as `HTTP 400: <error>`, the form the Python CLIs already used, instead of "coordinator rejected the request". The Python coordinator still appends to a file it can read in these cases, and answers 500 for one it cannot, until its own fix lands (Cohexa-ai/agent-coherence#284).

- **A session that only read a file is no longer told its EXCLUSIVE grant was revoked** ([#163](https://github.com/Cohexa-ai/agent-coherence-plugin/issues/163)). The Node coordinator queued a preemption notice for every peer it invalidated, readers included, at three sites: a peer's pre-edit, commit and CAS commit. So a session that had merely read `a/plan.md` was told "Your EXCLUSIVE grant on this artifact was silently revoked" as soon as another session edited it, a grant it never held. Those false notices also crowded out real ones: a session that read four files and held one write grant saw three of the reads in its next notice block, with the one grant it actually lost pushed behind "Plus 2 more" until a later hook. Of those three sites, the Python coordinator sends a notice only on pre-edit, and only to a peer that held EXCLUSIVE or MODIFIED; Node now does the same: a commit or CAS commit can only invalidate readers (one requires the caller to hold the write grant, the other refuses while any peer holds one), so they queue none. Readers are still invalidated and still get the stale-read warning on their next read of the changed file; only the misleading notice is gone. It also closes the strict-mode path to the same-second rename described in the entry below about a notice naming a session that no longer held the grant; the registry's `>=` guard stays.

- **A strict-mode denial now names the file it denied, whatever characters the path contains** ([#164](https://github.com/Cohexa-ai/agent-coherence-plugin/issues/164)). Both deny texts were built with chained `replaceAll` / `replace` calls that passed the path as a replacement *string*, and a replacement string is not literal: `$&` inserts the matched placeholder, `$$` collapses to `$`, and `` $` `` / `$'` splice the surrounding template into the path. The chain also re-scanned what it had just inserted, so a path containing `{last_writer_short}`, `{last_writer_ts_iso}` or `{current_version}` took that value while the real placeholder shipped unexpanded. `docs/a$&b.md` was reported to the model as `docs/a{path}b.md`, a path it would then go and re-read. Both texts now render through the single-pass `fmt()` that SessionStart already used, which inserts each value once and never re-reads it, exactly as Python's `str.format` does; `fmt()` moves to `hook_payloads.ts` so both renderers share it. Only `permissionDecisionReason` was ever wrong: the decision, and the coordinator state after it, were unaffected. A test asserts Python's exact bytes for every affected token on both texts, with controls (`$1`, `routes/$id.tsx`, a path containing `{path}`) that already rendered correctly and must keep doing so; each text's half fails on its own when its old chain is restored.

- **Strict mode no longer lets a session write a file it was just refused a read of.** A strict-mode deny of a Bash or Grep read re-grants the session's read so that the retry the deny invites can run, and records nothing as read, because the denied command never ran. The strict check on `Edit` and `Write` looked only for a session the coordinator had invalidated, so that re-granted read also admitted the session's next edit: a whole-file `Write` from the copy it read before a peer's commit then overwrote the commit, with nothing denied after the shell read (Cohexa-ai/agent-coherence#275). An `Edit` or `Write` of a strict path is now denied while the session's last read of it is older than its current version; re-running the Bash command or reading the file with `Read` records the current version and lifts it (after a Grep deny only a `Read` does, because a Grep lists files rather than showing them). A session that has never read the file at all is still treated like a first-time editor. Pinned by two protocol-corpus fixtures the Python coordinator shares.

- **A Bash or Grep command denied in strict mode no longer counts as a read.** When `pre-bash` or `pre-grep` finds a stale tracked file, it re-grants the session SHARED. It does this in strict mode too: the deny fires once, and a retry goes through. That grant also recorded the file's current version as the session's `last_observed_version`, even though a denied command never runs. After a compaction, the re-grounding stale flag then stayed silent for a file the session had never read at its current version. The same false baseline would have made the grant-change denial described above tell a session that nothing had been written since "the version you last saw", a version it had been refused. The grant is now issued after the deny decision, and it records the observation only when the command will run. That holds for every file the command named, including warn-only ones in a denied command, and for a first-seen file registered by a denied command. The grant itself is unchanged. An allowed command still records the read, because it does read the current bytes. So does the retry the deny invites: a session that already holds the grant and reads the file again, through a retried Bash command or a Read, now has the current version recorded as seen. Without that, a strict session that recovered this way kept its baseline from before the deny, or none at all on a first touch, so a later grant handover was reported as a write it had already read and a first-touch file lost its post-compaction stale flag. A Grep is not credited for a file the session already holds: it names every tracked file under its root, not what it showed, so the baseline stays behind until a Read. `grantShared` is a no-op on a SHARED row, so the read is recorded by a new registry call, `recordObservation`, which moves only the baseline and only for a SHARED holder. The Python coordinator changes identically in `agent-coherence` releases after 0.14.1, and the protocol corpus pins both directions on both backends.

- **Provisioning now recovers the HTTP status of a failed prebuilt download, so a transient 503 stops reading as a possibly-permanent platform gap.** The classifier added a release earlier said a missing asset and a transient failure were "genuinely indistinguishable here". They are not — that was a limitation of the invocation, not of the world. `prebuild-install` logs the status with `log.http(res.statusCode, url)` and gates it on `npm_config_loglevel`, which npm passes down from `--loglevel`; unflagged, its own `'notice'` default drops everything at `http` level, so the status was never printed by anyone and could not be recovered afterwards — not from npm's debug log either, since suppression happens inside the child. The install now asks for it. This matters most in one direction: `download.js:56` calls `onerror()` with **no argument** on any non-200, so every 5xx and 429 collapsed into the same "No prebuilt binaries found" string as a genuinely absent asset, and the hint could only shrug. It now branches — 404 reports that no prebuilt is published for this platform/arch/libc while deliberately **not** calling that permanent (a release can 404 mid-publish, an unsynced binary-host mirror 404s, and blocking proxies 404 the hosts they disallow), and a 5xx/429 reports the status and says plainly that it is transient. When no status was captured the old honest wording stands. The flag's cost is real and is paid on the **success** path: at `http` level npm logs one line per package, measured at 148 lines / 16KB warm and 298 / 31KB cold on this repo's own tree, and because this script's stdout is a SessionStart hook's stdout that lands in the model's context — several times the 10,000-byte ceiling, in registry chatter, which would evict the diagnostic it came for. So the raise is paired with a display filter (`| tee "$npm_log" | grep -v '^npm http \(cache\|fetch GET 200\)'`) that leaves the visible output matching the unflagged run apart from npm's own "added N packages in Xs" duration line (which differs between any two runs regardless of the flag — measured, not assumed), while the captured log keeps everything; `prebuild-install`'s own lines survive because npm prefixes them `npm error `, not `npm http `. `PIPESTATUS[0]` still carries npm's status through the three-stage pipe, verified, and the assignment stays on the line immediately after it because the next command clobbers it. Two things the review then pinned rather than trusted: the stub `npm` in the tests now models prebuild-install's own gating, emitting its `http` line only when `--loglevel=http` was actually passed, so deleting the flag from the script fails the suite instead of leaving it green; and only 5xx/429 are reported as transient, because a 403 from a blocking proxy or a 401 from a bad auth token is a refusal, and telling that operator to retry sends them round a loop that cannot succeed.

- **The admit-path preemption drain is bounded, so a pile-up no longer pushes `additionalContext` past what the platform delivers.** Every tracked-file admit hook drained an agent's entire pending-notice queue and rendered one bullet per notice, uncapped. On a workspace of this project's size that composed roughly **1.8x** the 10,000-byte ceiling -- and above that ceiling Claude Code does not truncate, it persists the prose to a file and hands the model a ~2KB preview plus a path, so the coherence notice becomes a pointer the model has to go and open. The bound is on the **consume**, not the render, which is the distinction a previous attempt ([#150](https://github.com/Cohexa-ai/agent-coherence-plugin/pull/150), closed unmerged) got wrong: `popPendingNoticesForAgent` now takes a `consumeLimit` that bounds the `DELETE` only, while the `SELECT` and the return value stay whole. The caller therefore renders the newest three, reports the **true** pending total in the intro, computes the overflow count as arithmetic on data it still holds, and leaves the remainder in the table -- which is what makes "still queued, they surface on your next tracked-file operation" a true sentence rather than the false one a render-only cap prints over rows it just deleted. This mirrors Python's `pop_pending_notices(consume_limit=)` exactly, including the value (3). The reasoning previously recorded in-source -- that a bound here needed a TTL sweep as a co-requisite -- was answering the render-cap design; a bounded consume drops nothing, so nothing needs reclaiming for correctness. The three near-identical inline drains in `pre_read`, `pre_edit` and `pre_bash`/`pre_grep` are now one helper in `hooks/_common.ts`, because three copies of a bound is three chances for one to drift. Measured end-to-end on `/hooks/pre-read` at 80 notices with 60-char paths: **11,037 to 2,022 bytes**, and the composed size is now independent of the notice count (2,076 B at 8 notices versus 2,022 B at 80). Cross-backend parity re-verified: the protocol corpus passes 61/61 against the bounded build. The bound holds on both axes: independent of the notice count, and still fitting at the longest path the policy admits (8,973 bytes at 80 notices with 1,020-character paths, against a `MAX_POLICY_PATH_LEN` of 1024). Getting the second axis required one more fix than the cap itself: the deferred re-grounding block is rebuilt at attach time, so once the drain stopped emptying the queue it began peeking the tail and rendering a SECOND notice block — whose intro reported the remaining count as though that were the number of grants revoked, handing the model two contradicting totals for one backlog and rendering rows the first block had just promised for next time. `buildSessionStartContext` now takes `includeNotices`, which the deferred seam passes false; the real `/hooks/session-start` endpoint is unchanged. That alone took the 800-character-path case from 10,216 bytes to 7,429. One property is worth knowing rather than fixing: because `nowTick()` floors to whole seconds, a burst of preemptions inside one second ties on timestamp and falls through to an `artifact_id` tiebreak over random UUIDs, so the cap now selects WHICH notices render rather than merely ordering them -- measured as five different rendered sets across five runs of one scenario. Nothing is lost and the choice is among simultaneous events, but it is why no `protocol_corpus` fixture pins this pile-up: a fixture asserts exact bytes and these are not stable across runs.

- **The provisioning failure message no longer blames your Node version for a dropped connection.** When `npm install` fails, `bin/ensure-coordinator-node` prints a hint. It used to assert, unconditionally, that a `No prebuilt binaries found` / node-gyp trace above "means this Node major lacks a better-sqlite3 prebuilt". That trace appears for *every* install failure, because better-sqlite3 falls back to compiling from source whenever it cannot place a prebuilt binary — for any reason, including a prebuilt download that was reset mid-flight. So a transient network failure presented as an unsupported-Node-version diagnosis, sending the reader to change Node majors when a retry was the fix. Observed for real on 2026-09-20: the `Zero-Python install (Node 24)` job failed with a full `gyp ERR! find Python` trace on a Node major that is supported and whose prebuilt (ABI 137) has shipped since June; the only discriminating line in the whole log was `prebuild-install warn install read ECONNRESET`, and a rerun went green. The hint now **classifies** rather than guesses: `prebuild-install` logs the deciding fact itself (`log.warn('install', err.message)`), so the warn line reads `No prebuilt binaries found (target=…)` for a genuine ABI gap and carries the transport error otherwise. The branches are ordered so the discriminating signal wins: `ESTRICTALLOWSCRIPTS` first, because it is a terminal npm error code rather than a warning and a tree with several native dependencies can carry both it and a `prebuild-install warn` line; then the prebuilt cases; then an explicit *unrecognised* case that no longer invents a cause. A first version of this classifier got its own premise wrong in the opposite direction, and the correction is the substance here: **`No prebuilt binaries found` does not mean the ABI is unsupported.** `prebuild-install` emits it for *any* non-200 response — `download.js` does `if (res.statusCode !== 200) return onerror()` with no argument, and `onerror` falls through to `error.noPrebuilts(opts)` — so a 404 or a 503 from the release CDN produces the identical string. Since Stage 0 has already refused to run on a major outside 22/24/25, that branch could only ever fire on a **supported** major, where "switch Node majors" is impossible advice printed directly under "supported majors are 22 / 24 / 25; running v24.x". The message's own `target=` field is now the discriminator: when it disagrees with the running major the ABI wording stands (defensive, and unreachable past Stage 0), and when it agrees the hint says a prebuilt could not be *placed* for this platform, that this is not the Node version, and that one retry is worth trying because a missing asset and a transient non-200 are genuinely indistinguishable here — prebuild-install logs the HTTP status at `http` level, below npm's default threshold, and it is absent from real failure logs. Each branch is pinned by a test that drives the real script with a stub `npm` emitting a canned log, asserting both the cause it must print and the cause it must **not**; the capture itself is covered too, since a failed `mktemp` skips every branch and must say the output was never examined rather than reporting no recognised cause in output it never read. A `trap` removes the log on paths that skip the in-line cleanup — a cold install regularly outruns the SessionStart hook's time box, and every timed-out provision used to leave a full npm log in `TMPDIR`.

- **A preemption notice could name a session that no longer held the grant.** `upsertPendingNotice` guarded its `ON CONFLICT DO UPDATE` with `WHERE excluded.preempted_at_unix_ts > pending_notices.preempted_at_unix_ts` — a strict `>` — while the same function's own docstring promised "latest preempter wins". Those disagree, because the timestamps are **whole seconds**: two preemptions of the same (victim, artifact) pair inside one second are indistinguishable by time, so the strict comparison declined the second and left the row naming the session it had already replaced. The model then read a bullet attributing the preemption to the wrong peer, which is the operator's only record of who took the grant. Reaching it requires the victim to re-arm a grant **without** draining its notice queue. When this was found, the strict-mode path did exactly that: `pre_bash` (and identically `pre_grep`) re-grants SHARED to suppress repeat fires, then returns the deny *before* `drainNoticeText`, and that reader was then queued a second notice. This was twice recorded on [#138](https://github.com/Cohexa-ai/agent-coherence-plugin/issues/138) as reachable only synthetically; it was reachable over the real hook surface. The fix for [#163](https://github.com/Cohexa-ai/agent-coherence-plugin/issues/163) in this release stops queueing notices for readers, which closes that path: the end-to-end test through `/hooks/pre-edit` → strict `/hooks/pre-bash` → `/hooks/pre-edit` → `/hooks/pre-read` now pins that the re-grant earns no second notice, and a registry-level test pins the state transition itself. The guard is now `>=`, which makes it last-write-wins within a second while still refusing a strictly **older** timestamp — the only ordering the comparison was ever load-bearing for, and itself pinned by a test. Python's `sqlite_registry` carries the identical strict `>` and correctly keeps it: the two backends feed that comparison different clocks. Node stamps `Math.floor(Date.now() / 1000)`, so two preemptions of one pair inside a second tie exactly and the strict form declines the second; Python is handed float `time.time()`, where two preemptions on separate requests do not collide. So there is no drift to reconcile and nothing to track — the tripwire is the clock, and it is recorded beside the guard itself in the library repo rather than in a ticket, because coarsening those timestamps is the change that would break it.

- **Warn-mode prose no longer promises a surface that cannot answer, and no longer spells timestamps in a dialect the Python coordinator never writes.** Three defects on the same model-visible surface. (1) When more preemption notices arrive than session-start renders verbatim, the overflow line reused the *artifact* template — "run `agent-coherence-status` for the full picture" — but `GET /status` carries `tracked_artifacts[].path/.version` and no notice data at any disclosure tier, so a coalesced notice pointed the model at an endpoint that cannot answer it. The notice block now has its own line saying the rows are still queued and surface on the next tracked-file operation, which is literally true because session-start peeks the queue rather than popping it (R6). (2) `selectPendingNoticesForAgent` had no `ORDER BY`, so rows came back in `artifact_id` order — and artifact ids are random UUIDs, uncorrelated with preemption time. Harmless only while every caller drains and renders the whole queue; it now sorts newest-first like Python's `pop_pending_notices`, which is the prerequisite any bounded consume needs to delete the same set it rendered. (3) Every stale-read warning, edit-collision warning and preemption bullet formatted instants with `Date.toISOString()` (`…T12:00:00.000Z`) while the strict-deny path alone used the module's own `pythonIsoUtc`, which reproduces `datetime.isoformat()` (`…T12:00:00+00:00`) — so the highest-volume prose on the admit path byte-diverged from the canonical backend on every timestamp it printed. The cross-backend protocol corpus could not see this: its harness normalizes both spellings to the same `<TS>` placeholder. Verified instead by differential comparison against real Python across six instants (zero-fraction, `.5`, microsecond, `.999999`), byte-identical in every case.

### Security

- **The policy writer no longer follows a symlink planted at its temporary-file path** (CWE-59). `/policy/track` and `/policy/untrack` wrote the new policy to a fixed `.coherence/tracked.yaml.tmp` (or `ignored.yaml.tmp`) with a plain write, which follows a symlink, then renamed it over the policy file. A repository that committed that path as a symlink had the link's target overwritten with the policy contents on the next track or untrack, and the policy file itself replaced by the link. The writer now uses a per-write random name created exclusively (`O_CREAT|O_EXCL`), the pattern the caller-principal store already uses, and removes it if the rename fails. Present since the Node writer was introduced.

### Internal

- **Dependabot version updates target `dev` again, and `main`'s merges flow back to `dev` automatically.** Commit 3a1d0ca (2026-07-17) pointed version updates at the default branch on the premise that `dev` mirrored `main`. It has not since: `dev` runs ahead between releases, so Dependabot bumps landed on `main` first and reached `dev` only through hand-made forward-merges: six so far (#109, #112, #141, #147, #160, #182), four of them carrying Dependabot bumps. `.github/dependabot.yml` sets `target-branch: "dev"` on both ecosystems, so version bumps land on the integration branch and reach `main` with the release; that takes away no human review, because what merges unattended is decided by `dependabot-automerge.yml`'s gate on either branch, and it keeps unreviewed bumps off `main`, which unpinned marketplace installs track. What still lands on `main` by platform design (Dependabot security updates, including transitive fixes that a version update never produces) and by process (the release merge and bump, hot-fixes) is merged into `dev` by a new `forward-merge-main` workflow, on push to `main` and four times a day. It acts as a GitHub App rather than `GITHUB_TOKEN`, because `GITHUB_TOKEN` cannot push changes to `.github/workflows/`, gets its PRs' checks held for approval, and fires no push workflows. The App's key lives in a `forward-merge` environment that only `main` may deploy from, because the App can approve PRs and `dev` takes unreviewed merges; the workflow ignores fork PRs that reuse its branch name, pins every merge to the commit it pushed, and runs no `actions/checkout` beside the key. `docs/RELEASE.md` §1 has the one-time App and environment setup, and §2 and §3 now point at the workflow. A conflict fails the run red for a hand merge rather than being resolved. `dependabot-automerge.yml` now auto-merges npm devDependency patch/minor bumps only: GitHub Actions bumps are third-party code that runs inside workflows holding write tokens or the App key, so each waits for a human (none had ever auto-merged in practice, because GitHub refuses auto-merge with that token on a PR that edits a workflow). Its comments no longer claim a squash-only `main` or an approval setting that is off.

## [0.5.0] — 2026-08-25

**A compacted session no longer forgets what it held: the coordinator re-grounds it — grants at compaction, plus which artifacts peers moved — and provisioning survives Node major upgrades, script-blocked installs, and stale builds.**

### Added

- **Compaction-aware re-grounding.** When Claude Code compacts a session (auto or manual `/compact`), a second `SessionStart` hook entry now fires `hook-client session-start`, which gates on `source=compact` client-side and asks the coordinator's new `POST /hooks/session-start` endpoint for a re-grounding payload: the grants the session held at compaction (event-anchored prose) and each touched artifact's current coordinated version with a stale flag when a peer advanced it past the session's last-observed version (a new nullable `last_observed_version` column on `agent_states`, migration v4, recorded in-transaction at grant and commit time). The payload renders at the next user message and on `--resume`; a live autonomous loop additionally receives it on its next tool admit via a coordinator-side compact-pending flag claimed exactly once at the allow seam — strict-mode deny bodies stay byte-identical and never carry it. Payload prose is byte-identical to the Python coordinator's and pinned by six new protocol-corpus fixtures; capped at three artifact lines plus an overflow summary; empty sessions emit nothing. One benign residual duplicate is documented (mid-loop delivery followed by the next user turn's attachment render) and the closing self-qualifying line makes a second sighting harmless.
- **The release preflight now fails on a branch ruleset that forbids the documented release merge.** `main` is guarded by two independent systems — classic branch protection and the `protect-main` ruleset — which stack and are evaluated separately, and `tools/check_release_readiness.js` only ever inspected the first (plus the *tag* ruleset, a different object with different rules). The second drifted unseen into `allowed_merge_methods: ["squash"]` with `required_linear_history`, directly contradicting `docs/RELEASE.md` §2 step 2, which merges the release with a merge commit. v0.4.0 paid for it: the release was squash-merged, `main` was left with no ancestry link to `dev`, and the next forward-merge came back as add/add conflicts across every file the release touched, resolved by hand in [#112](https://github.com/Cohexa-ai/agent-coherence-plugin/pull/112). Preflight reported **0 failures** the whole time. A new check asserts that any active branch ruleset covering the default branch omits `required_linear_history`, includes `merge` in `allowed_merge_methods` (an absent list means all methods are permitted, and is accepted), and carries an admin bypass actor — without which `main`'s structurally unsatisfiable review requirement makes every release unmergeable. The rule logic is a pure exported function (`evaluateBranchRuleset`) so `src/test/release_readiness_branch_ruleset.test.ts` exercises it with no network round-trip, pinning the exact v0.4.0 shape as a failing case. One visibility subtlety: `bypass_actors` is an admin-scoped field GitHub omits entirely for non-admin viewers — the release workflow's own `GITHUB_TOKEN` included — so from CI the bypass sub-check downgrades to a verify-locally warning instead of failing a correctly-configured release; the merge-method and linear-history sub-checks (whose fields are always visible) stay hard everywhere, and a *visible* bypass list without an admin actor still fails.

### Fixed

- **A Node major upgrade no longer kills the coordinator permanently.** Provisioning was keyed on a `diff` of `package.json`, which detects a *package* change but is blind to a *Node ABI* change — and native-module validity depends on `process.versions.modules`, which `package.json` cannot express. Provision under Node 23 (ABI 131), install Node 24 (ABI 137), and every session from then on crash-looped `The module '…/better_sqlite3.node' was compiled against a different Node.js version using NODE_MODULE_VERSION 131. This version of Node.js requires NODE_MODULE_VERSION 137.` with nothing to break the cycle. A package bump did not rescue it either: the 0.3.1 → 0.4.0 diff *did* fire, but `npm install` saw `better-sqlite3` already present at a satisfying version and skipped it, leaving the ABI-131 binary exactly where it was. `bin/ensure-coordinator-node` now stamps the provisioning ABI to `${CLAUDE_PLUGIN_DATA}/.node-abi` and treats a mismatch as an install trigger alongside the `package.json` diff, **tearing down `node_modules` before installing** so `prebuild-install` refetches the prebuilt for the running ABI (`npm rebuild` is deliberately not used — it compiles from source via node-gyp, and the plugin's zero-Python install path forbids a compile-time toolchain dependency). Trees provisioned before the stamp existed are probed rather than reinstalled, so upgrading costs a healthy install nothing and needs no network; and a `NODE_MODULE_VERSION` death at the post-spawn liveness gate invalidates the stamp, turning any remaining case of this failure into one bad session instead of a permanent one.
- **A silently script-blocked install is now caught at provision time instead of at first query.** `better-sqlite3`'s install script *is* `prebuild-install` — the prebuilt download itself — so an `ignore-scripts` in any npmrc yields a tree that installs "successfully" with no binary in it. Stage 1 now verifies the addon actually loads (constructing a `Database`, since `bindings` resolves the `.node` file lazily and a bare `require` succeeds against a missing binary) before stamping the ABI, and fails loudly with the likely cause rather than spawning into a crash loop. Relatedly, npm 11 gates install scripts behind an `allowScripts` allowlist: `package.json` now covers `better-sqlite3` explicitly, which both silences the default warning and keeps provisioning working for users whose npm config sets `strict-allow-scripts`. The zero-Python CI job and its install-time assertion run with that flag on, so any dependency that grows an install script fails CI until it is covered deliberately.
- **A plugin update that changes `src/` without bumping the version no longer serves a stale `dist/`.** Stage 2's rebuild key had the same shape as the ABI bug — `package.json` as a proxy for "the package changed" — so on the marketplace (dist-less) path the compiled output could outlive the sources it came from. The rebuild now also triggers when `src/` or `tsconfig.json` is newer than the built entry point.

## [0.3.0] — 2026-07-24

**Zero-Python Node coordinator + composite subagent identity.** The Node backend reaches full parity with Python — no Python install required for any surface, including strict mode — and subagents become first-class coherence peers via composite identity (SB-25).

### Added

- **Zero-Python Node coordinator.** The Node backend is now self-sufficient — a fresh install on a machine with no Python yields a complete working setup: all six hooks via a Node hook-client, the `track`/`untrack`/`status` CLIs, five previously Python-only routes (`/hooks/pre-bash`, `/hooks/pre-grep`, `/hooks/post-edit-cas`, `/policy/track`, `/policy/untrack`), and **strict mode** at byte-parity with Python. Absent/malformed `agent_id` resolves to the parent identity (an absent OR malformed id on subagent-stop is a no-op, never a parent-scoped release).

### Fixed

- **subagent-stop could release the parent's grants on a malformed `agent_id`.** A present-but-malformed `agent_id` passed the client's non-empty check, was nulled server-side, and degraded to a parent-scoped release. The client now shape-validates the id (both Node and Python) and the coordinator fails closed on a present-but-invalid id.
- **A subagent's own just-committed file was strict-denied as a "foreign edit."** The self-commit-lag suppression compared a derived session string against the parent `session_id`; it now compares the raw writer identity against the caller's composite agent id (both backends).
- **ReDoS in the Bash tracked-path detector.** The Node port had dropped Python's negative-lookbehind, so an adversarial dot-free command drove near-quadratic regex backtracking that blocked the single-threaded coordinator; the lookbehind is restored.
- **Unbounded `git` calls in coordinator discovery.** `findCoordinatorRoot` now bounds every `git` invocation with a 5s timeout (matching Python), preserving the always-exit-0 fail-open contract when `git` hangs.
- **`artifactNamesUnderPrefix` directory-boundary bug.** A bare prefix over-matched sibling directories (`docs/specs` → `docs/specs-internal/`) and returned nothing for a `.` search root (silently skipping the whole pre-grep stale check); it now mirrors Python's normalization (empty/`.`/`./` → all; trailing-slash boundary; exact-match UNION).
- **Policy-path validation gaps + wire divergence.** `/policy/track`/`untrack` now reject control characters (closing a YAML newline-injection vector), leading backslash, and over-long paths, with rejection reason strings byte-identical to Python (both now corpus-guarded).
- **Cross-runtime migration-ledger collision on the shared `state.db` ([#55](https://github.com/Cohexa-ai/agent-coherence-plugin/issues/55)).** The Node coordinator now fails closed when it opens a `state.db` written under the sibling Python coordinator's ledger, instead of running its own v3 migration on it (which added `agent_states.deadline_tick` and stamped `user_version=3`, after which the Python coordinator refused to reopen its own store). Detection mirrors the Python guard: a foreign `registry_meta.schema_runtime` stamp, the Python-only `artifact_versions` table, or the Python `artifacts.owner_generation` fence column raise a typed `CrossRuntimeSchemaError` (`reason = "cross_runtime_schema"`) before any migration runs. Node now stamps `registry_meta.schema_runtime = "node"` on create and back-fills it on migrate, so detection is symmetric from both sides. `user_version == 1` remains indistinguishable by design (the Node v1 schema mirrors Python v1 byte-for-byte).

### Changed

- **Removed destructive `rm state.db` recovery advice.** Now that the shared store holds durable retained version content and live coordination state, the schema-mismatch error, the v2 shape-mismatch error, and the README troubleshooting rows no longer advise deleting `state.db` / `.coherence/`; the secret-rotation step removes only `.coherence/hook.secret`.

- **`hook.secret` rotation is MANDATORY on v0.2 upgrade** per KTD-W. Secrets generated under v0.1.1's warn-mode threat model gate v0.2's strict-mode hard guardrails — inherited entropy is insufficient to bridge the upgrade. Documented in [docs/RELEASE.md](docs/RELEASE.md) section 4 and the README FAQ. Procedure: stop running `claude` sessions → `rm <repo>/.coherence/hook.secret` → restart any `claude` session, which lazy-spawns the coordinator and generates a fresh 32-byte secret.
- **`.claude-plugin/marketplace.json` description** — removed "Warn-only in v0.1.1" framing now that v0.2 ships strict mode.

### Backend compatibility

- **Strict mode is Python-coordinator-only in v0.2.** Workspaces using `coherence.coordinator_backend = "node"` stay warn-mode. v0.3 brings the strict-mode wire shape to the Node coordinator behind the multi-target converter plan.
- Library version requirement: `agent-coherence>=0.8.0` for warn mode; `agent-coherence>=0.9.0` for strict mode (the v0.9.0 library release ships the wire-shape additions).

### Known limitations

See the README [v0.2 known limitations](README.md#v02-known-limitations) table for the full list. Most-relevant for broad-beta operators:

- Native Windows still requires WSL2 (`fcntl` constraint).
- Bypass classes: interpreters outside the `bash_path_detector` list (`ruby -e`, `node -e`, `perl -pe`), shell-redirect reads (`tee < file`), and `diff /dev/null file` patterns can read strict-tracked artifacts. The migration helper closes the interpreter class via `permissions.deny`; shell-redirect and diff-as-reader are terminal limitations or v0.2.x backlog.

### Added — Node MESI-subset coordinator

- **One-click marketplace install** via the Node coordinator backend (`coherence.coordinator_backend = "node"`). Mirrors the Python coordinator's HTTP wire contract; both backends share the `hook.secret` exchange and `server.pid` lazy-spawn semantics. Switch via `agent-coherence-coordinator --prepare-for-migration` for safe Python ↔ Node transitions.
- **Multi-tool hook routing (H4 mitigation)** — `hooks.json` matchers cover `Read`, `Edit|Write`, `Bash`, `Grep`. Closes the model-routing-around-Read pattern Phase 0 confirmed (model retries denied Read 2-5 times then falls back to `bash cat plan.md`).
- **AC-02 + AC-03 wire-shape parity** — Node and Python coordinators emit aligned `/status` shapes: `coordinator_uptime_seconds` (canonical name, full-word `_seconds` suffix), `sessions[].agent_name` + `sessions[].states` (per-agent MESI snapshot).

### Added — operator-facing tooling

- **`agent-coherence-status --self-test`** — post-install 4-step pre-read → pre-edit → post-edit → stale-pre-read smoke. Exit 0 on pass, 3 with actionable diagnostic on fail. The single-best signal that the install wired up hooks correctly.
- **`agent-coherence-coordinator --prepare-for-migration`** — atomic draining state that releases all M/E grants + rejects new pre-edit (HTTP 503) + shuts down. Eliminates silent data-loss races when switching Python ↔ Node backends.

### Security

- **Bearer-token auth** on every coordinator endpoint with constant-time comparison (`crypto.timingSafeEqual` / `hmac.compare_digest`). Token stored as `<repo>/.coherence/hook.secret` mode `0600`, created atomically via `O_WRONLY | O_CREAT | O_EXCL`.
- **Host-header allowlist** (`localhost` / `127.0.0.1` only) rejects DNS-rebinding from non-loopback origins before token comparison.
- **R12 three-tier `/status` disclosure** — default `minimal` tier is safe to paste in bug reports (no absolute paths, no PIDs, no session identifiers); `?detail=metrics` adds telemetry; `?detail=full` requires `Coherence-Local-Operator: true` opt-in header for the elevated tier.
- **R21 64KB request body cap** + **R11 bounded `O_EXCL` retry** on empty-secret recovery (fail-closed after 5 attempts).
- **CycloneDX SBOM** attached to every GitHub Release via `release.yml`.

### Plugin coexistence

- `package.json` is `"private": true` by design. Distribution is via the Claude Code marketplace catalog, not npm. The plugin is consumed via `/plugin marketplace add Cohexa-ai/agent-coherence-plugin@v0.1.1`, which clones the tagged Git ref directly.
