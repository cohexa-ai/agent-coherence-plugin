# Changelog

All notable changes to the `agent-coherence` Claude Code plugin are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions adhere to [SemVer 2.0](https://semver.org/spec/v2.0.0.html).

Alpha — APIs and the `hooks.json` wire shape may change before `v1.0`.

The canonical release-notes surface is [GitHub Releases](https://github.com/Cohexa-ai/agent-coherence-plugin/releases); this file mirrors that history in a structured format for operators who prefer a single browsable timeline.

## [0.6.0] — 2026-10-13

**Strict mode no longer lets a session write a file it was just refused a read of; `/status` and hook messages stop publishing raw session ids and your absolute workspace path; tracking a `*` glob can no longer empty a policy file; the status, track and untrack commands escape what the coordinator sends and report refusals by exit code; and the hook client is ready for the caller principal that `agent-coherence` releases after 0.14.1 issue.**

**Upgrade note:** on the Node backend, `GET /status` now reports every session's `agent_name` as `null`; key on `agent_id` instead. `agent-coherence-untrack` now exits 3 when a Python coordinator from a release after 0.14.1 refuses to untrack a strict path, and `agent-coherence-status` exits 2 when the coordinator's registry is busy; scripts that read these exit codes may need updating. Track and untrack now refuse, with `HTTP 400` and exit 2, a policy file that an earlier unquoted write broke or that is not a plain list. Releases 0.3.0 to 0.5.0 wrote a pattern that starts with `*` unquoted, which makes the whole file load as no entries: after upgrading, check `.coherence/tracked.yaml` and `ignored.yaml` and quote any such entry (`- "*.md"`).

### Added

- **On a Python-backend workspace the hook client now claims a caller principal and sends it with every hook, so the coordinator can refuse a request for that session from a client that never claimed it.** In `agent-coherence` releases after 0.14.1, the Python coordinator binds a caller principal to a session the first time a client claims it (`POST /principal/claim`). From then on it refuses a request naming that session without the principal on the routes where an unbound caller could do harm (pre-edit, post-edit and session-stop among them), and refuses a wrong principal on every route. The plugin's Node hook client now takes part. On a session's first hook it writes a random claim nonce to `.coherence/caller-principal-<agent id>.nonce`, claims the principal with it, stores the principal beside it in a `.principal` file (both mode `0600`), and sends it on every later hook in a `Coherence-Caller-Principal` header. The file names and formats are the Python hook client's, so both clients share one binding per session. The coordinator may refuse the principal, for example after losing its bindings because `state.db` was removed or restored, or because a claim's answer never arrived. The client then claims again with the same stored nonce, stores what comes back and retries the refused hook once. It never makes a new nonce, so it cannot take over a session another client has claimed. A hook it cannot recover fails open with `{}` and one line on stderr saying why, and nothing it prints contains the principal, the nonce or the coordinator's own error text. This is not a boundary between local processes: anything running as your OS user can read `.coherence/`. The Node coordinator issues no principals and ignores the header. The client reads `backend=node` from `server.pid` and does not claim, so a Node workspace sends exactly the requests it did before. Against `agent-coherence` 0.14.1 or earlier, which has no claim route, the client still writes the nonce file, and each hook makes one extra local request that the coordinator answers with 404, then proceeds without the header.

### Changed

- **`/status` no longer publishes a raw session identifier.** Each session row
  carried `agent_name` as `claude-session-<session id>`, beside the
  non-reversible `agent_id`. This coordinator serves no `detail=full` tier, so
  the tier rendering it was the only tier it has; `agent_name` is now `null`,
  and `agent_id` and the per-artifact states are unchanged. In
  `agent-coherence` releases after 0.14.1, the Python coordinator redacts the
  same field below its operator tier, so both backends now return `null` for
  `agent_name` below the operator tier.

- **A hook response names a peer by agent id, and a denial no longer reports a
  write that did not happen.** The last-writer field on stale responses and
  strict denies carried a peer's raw session id, reversed out of the agent id
  by a lookup that has been removed rather than left unused. A denial issued
  when a peer merely took the grant also claimed the artifact "was updated",
  naming a timestamp for a write that never occurred; that case now has its
  own message. Both texts are byte-identical to the Python coordinator's in
  `agent-coherence` releases after 0.14.1.

### Fixed

- **A warning that cannot name the other agent no longer prints a broken `<unknown` placeholder.** The stale-read warning, the edit-collision warning and the preemption-notice bullets shortened every identity to eight characters, the `<unknown>` placeholder included, so it reached the model with its closing bracket cut off: `another session (<unknown) has been editing docs/plan.md`. In 0.5.0 this happened after every coordinator restart, because those texts printed a session id from a lookup that starts empty in each coordinator process. They now name the peer by agent id, which is stored with the artifact and survives a restart (see the agent-id entry under **Changed**). The placeholder, still used when no writer is on record, is printed whole, as strict-mode denials already did.

- **`/agent-coherence:status` no longer prints the operator view when it falls back to the Python console script.** The command ran `agent-coherence-status` with no arguments. The shim runs the plugin's Node CLI, which asks for the default tier, but with no `node` or no built `dist/cli_status.js` (a Python-backend marketplace install, for one) it runs the library's console script, whose default was the operator tier with the `Coherence-Local-Operator: true` header; that path printed every session's name, which embeds the raw session id, and the absolute workspace root into the transcript. The command now runs `agent-coherence-status --detail minimal`, which every `agent-coherence` release from 0.9.0 accepts and both coordinators answer with the default tier, and the Node CLI accepts `--detail minimal` too, sending `?detail=minimal` without the operator header. `agent-coherence` releases after 0.14.1 also make the default tier the console script's own default.

- **The Node coordinator's default `/status` tier no longer publishes the absolute workspace root.** Its `policy_summary.coordinator_root` held the absolute path, and the status command prints the answer verbatim, so `$HOME` and the directory layout reached the transcript on every backend. It now reports `.`, as the Python coordinator's default tier does for the same key in `agent-coherence` releases after 0.14.1; the protocol corpus pins it on both backends instead of ignoring `policy_summary`.

- **`agent-coherence-status`, `-track` and `-untrack` now wait 6 seconds for the coordinator, as the Python console scripts do.** They gave up after 5 seconds. On a large workspace the Python coordinator's `--detail full` answer can take just over 5 seconds when a busy registry frees up late, and the CLI reported that as `request timeout` with exit 2. Hooks keep their 5-second limit.

- **`agent-coherence-untrack` now exits 3 when the coordinator refuses to untrack a strict path, and says what to do** ([#177](https://github.com/Cohexa-ai/agent-coherence-plugin/issues/177)). `agent-coherence` releases after 0.14.1 refuse to untrack a path `.coherence/strict_mode.yaml` enforces, answering with `reason: untrack_strict_path` and a `refused` list. The Node CLI printed that as a bare `HTTP 409` with exit 2, the same as any other failure. It now prints one line per refused path naming the strict patterns that enforce it, then says nothing was untracked and that the path stays enforced until its entry is removed from `.coherence/strict_mode.yaml` and the coordinator restarts, and exits 3, as the Python console script does. Any other refusal still exits 2. The Node coordinator does not refuse yet: on a Node workspace, untracking a strict path still removes it from strict mode.

- **The track and untrack CLIs no longer print coordinator text raw, and no CLI prints a coordinator error raw.** A path or reason in a track or untrack answer, and the error in any HTTP error answer or failed request, went to the terminal as it arrived, so an escape sequence could drive the terminal, a bidi control could reorder the line, and a newline could forge a second line. Each such string is now escaped exactly as the Python console scripts escape it: the same characters, written the same way, so both CLIs print the same line for the same answer. A rejected or refused path is quoted the way the Python scripts quote it. `agent-coherence-status` still prints the `/status` body as JSON, which escapes control characters but not bidi controls or line separators.

- **The track and untrack CLIs now reject an answer of the wrong shape instead of reporting success.** An answer whose `applied` was not a list of paths, or whose `rejected` was not a list of objects, printed nothing and exited 0. It now prints `unexpected <endpoint> answer shape` and exits 2, as the Python console scripts do. `agent-coherence-track` also warns when a path it tracked does not exist on disk yet.

- **`agent-coherence-status` now exits 2 when the answer carries no session or artifact lists.** When the coordinator's registry is busy, `agent-coherence` releases after 0.14.1 answer `/status` with `degraded: true` and no `tracked_artifacts` or `sessions` list. The Node CLI printed that body and exited 0, so a script reading the exit code took it for a workspace with nothing tracked. It still prints the body, then says the registry is busy and to try again shortly, and exits 2; any other answer missing those lists exits 2 with `unexpected /status shape`. `--detail metrics`, which carries no lists, is unaffected.

- **The status, track and untrack command docs match what the CLIs do.** `/agent-coherence:status` describes each tier by backend and version, and says what the "no coordinator" and "registry busy" messages mean; `/agent-coherence:untrack` explains exit 3; `/agent-coherence:track` no longer refers to an internal build step.

- **The README, PRIVACY.md, SECURITY.md and the bug-report template now match what the plugin and both coordinators do** ([#165](https://github.com/Cohexa-ai/agent-coherence-plugin/issues/165)). PRIVACY.md and the bug-report template no longer call the default `/status` tier safe to paste. They say what each tier carries on each backend: only the metrics tier is free of paths, process ids and session identifiers; the Python coordinator reports its process id at the default and full tiers, and 0.14.1 also reports the absolute workspace root and raw session ids there; the Node coordinator reports no process id at any tier. PRIVACY.md and SECURITY.md no longer claim the plugin makes no outbound requests: installing the Node backend's dependencies fetches packages from your npm registry and `better-sqlite3`'s prebuilt binary from GitHub, on the first session and after an upgrade that changes them. The README now says that:
  - an Edit or Write gets no stale-read line;
  - Stop releases committed (MODIFIED) grants as well as EXCLUSIVE ones, so a session's first read of a file it wrote in an earlier turn is reported stale;
  - a strict-mode deny is cleared by a Bash or Grep read run twice, not by a Read.

  It also lists the caller-principal files, the Python-library version each behavior needs, and four new known limitations: the caller principal's trust boundary, untracking a strict path on the Node backend, deny text that points the agent at the Read tool, and policy files an earlier release broke. SECURITY.md now says what `uuid` is used for.

- **The `--self-test` refusal no longer tells you to switch the workspace to the Python backend.** The bundled Node CLI rejects `agent-coherence-status --self-test` with exit 2, and the message offered `printf 'python\n' > .coherence/coordinator_backend` as one way to run it. On a workspace whose `.coherence/state.db` the Node coordinator created, that leaves no coordinator at all: the dispatcher honors the file verbatim, the Python coordinator fails closed on the Node ledger (`CrossRuntimeSchemaError`), and once the Node process exits every hook fails open with `{}`. `agent-coherence-coordinator --prepare-for-migration` is not a way around it: against a running Node coordinator it gets HTTP 404 and exits 2, because the Node coordinator serves no `/admin/prepare-for-migration` route; with none running it exits 0 without touching the store, and the Python coordinator still refuses it. The message now says the flag needs the Python library's console script, run by its install path (the plugin's `agent-coherence-status` shim prefers the Node CLI whenever `node` is on PATH), on a workspace the Python coordinator serves. It also says why: the self-test finishes by checking counters only the Python coordinator serves, so run against the Node coordinator it passes all four steps and still exits 3. On a Node workspace the message points at plain `agent-coherence-status` instead, as the README already does. The exit code is unchanged.

- **No message or doc tells you to switch a workspace's store to the other backend any more, because nothing can.** Each coordinator fails closed on a `state.db` the other created, in both directions, and `agent-coherence-coordinator --prepare-for-migration` drains and stops a running Python coordinator without converting anything; the Python coordinator still refuses a Node-created store afterwards, and the Node coordinator a Python-created one. Two Node-bootstrap refusals (an unsupported Node major, and a build that produced no `dist/coordinator.js`) printed `echo python > .coherence/coordinator_backend` unconditionally; on a Node-created store that leaves the workspace with no coordinator. They now offer it only while the workspace has no `state.db`, where the Python coordinator creates its own; with a store present they say to select Python only if the Python coordinator created it. The Node coordinator's `CrossRuntimeSchemaError` no longer refers to "the supported migration path" for moving a Python store to Node; it says no tool converts a store, and still says never to delete it. The README no longer says to switch backends "safely via `--prepare-for-migration`" (the binaries table, **Selecting the backend**, and the Architecture section), and Installing §B no longer says to opt an existing workspace into Node with `printf 'node\n'`, which on a Python-created store leaves it with no coordinator; it now says an existing Python store cannot move. **Selecting the backend** also warns that an explicit choice on a workspace with a store must name the backend that created it. The library's matching message is corrected separately.

- **`agent-coherence-status --detail full` can read the Python coordinator's operator tier.** The Node CLI requested `?detail=full` without the `Coherence-Local-Operator: true` opt-in header, so the Python coordinator answered 403 and the CLI printed "coordinator rejected the request" and exited 2, although 0.3.1 listed `--detail full` as honored. The CLI now sends the header for `--detail full` only; the default and `--detail metrics` requests are unchanged. A refusal now prints `HTTP <status>: <error>` (or `HTTP <status>` when the body carries no error), as track and untrack do, and a 2xx answer that is not JSON prints "coordinator returned a non-JSON response" instead of "coordinator rejected the request"; both still exit 2. The Node coordinator's 501 for `--detail full`, which the CLI now relays, used to read "detail=full not implemented in v0.1.1 unit 1"; it now says the operator tier is served by the Python coordinator only. It deliberately names no backend switch: a store the Node coordinator created is one the Python coordinator fails closed on, and `agent-coherence-coordinator --prepare-for-migration` does not convert it.

- **A coordinator answer cut off mid-body is now an error, not a silent success.** `requestJsonStatus` waited only for the response's `end` event, which never fires when the connection drops after the headers, so the request never settled and `agent-coherence-status`, `-track` and `-untrack` exited 0 with no output; a script read that as an empty success, and track or untrack as a confirmed change. An incomplete response now rejects as the network error it is: the CLIs print "coordinator closed the connection before the response was complete" and exit 2, and a hook still fails open with `{}`.

- **A policy file with long runs of blank lines no longer stalls the coordinator on every track or untrack.** The writer trimmed the file's trailing newlines with a `/\n+$/` replace, which backtracks over every run of newlines in the file and is quadratic in its length: 60,000 blank lines inside a list (well under the 64 KB cap) blocked the coordinator's only event loop for about 2.3 seconds per call. The trim is now a linear scan with the same result, 5 ms on the same file.

- **Tracking or untracking a pattern that starts with `*` no longer silently drops every other entry in the file** ([#178](https://github.com/Cohexa-ai/agent-coherence-plugin/issues/178)). `/policy/track` and `/policy/untrack` wrote each entry to `tracked.yaml` / `ignored.yaml` as a YAML plain scalar, `- ${p}`, and a plain scalar is not literal. A leading `*` is an alias, so untracking `*.log` stopped `ignored.yaml` parsing; the loader then fell back to no entries, every earlier ignore stopped applying, and the request still answered success. Several other leading characters (`!` `[` `{` `|` `%` `@` `` ` `` and quotes) break the file the same way; `&`, `#`, `key: value` and values such as `null`, `123` or `true` silently drop the one entry; and ` #` mid-path quietly turned `docs/x #1.md` into the pattern `docs/x`. Entries are now written as double-quoted scalars through js-yaml's own dumper, so every one reads back as exactly the string that was sent. The dumper rather than `JSON.stringify` because both backends read these files, and PyYAML folds a raw NEL (U+0085, which path validation admits) inside a quoted scalar to a space; the dumper writes it as `\N`. The Python coordinator writes the same double-quoted form in `agent-coherence` releases after 0.14.1, which fix the identical defect (Cohexa-ai/agent-coherence#284). Existing lines are left as they are. The writer now also refuses, writing nothing and answering 400, whenever an append could not take effect: a file an earlier unquoted write already broke (it loads as no entries, so the new entry never would either), a file that holds something other than a list, a valid list in a layout an appended line would break (a `[ ... ]` list, an indented list or a `...` end marker, where the write used to erase entries that were working), and a file it cannot read (which it used to treat as empty and replace with only the new entries). The message names the file, says where the parser stopped, and says how to rewrite it. The Node `agent-coherence-track` / `-untrack` CLIs now print that message as `HTTP 400: <error>`, the form the Python CLIs already used, instead of "coordinator rejected the request". In releases after 0.14.1 the Python coordinator refuses the same files with 400. 0.14.1 and earlier still write unquoted entries, append to a file they can read in these cases, and answer 500 for one they cannot.

- **A session that only read a file is no longer told its EXCLUSIVE grant was revoked** ([#163](https://github.com/Cohexa-ai/agent-coherence-plugin/issues/163)). The Node coordinator queued a preemption notice for every peer it invalidated, readers included, at three sites: a peer's pre-edit, commit and CAS commit. So a session that had merely read `a/plan.md` was told "Your EXCLUSIVE grant on this artifact was silently revoked" as soon as another session edited it, a grant it never held. Those false notices also crowded out real ones: a session that read four files and held one write grant saw three of the reads in its next notice block, with the one grant it actually lost pushed behind "Plus 2 more" until a later hook. Of those three sites, the Python coordinator sends a notice only on pre-edit, and only to a peer that held EXCLUSIVE or MODIFIED; Node now does the same: a commit or CAS commit can only invalidate readers (one requires the caller to hold the write grant, the other refuses while any peer holds one), so they queue none. Readers are still invalidated and still get the stale-read warning on their next read of the changed file; only the misleading notice is gone. It also closes the strict-mode path to the same-second rename described in the entry below about a notice naming a session that no longer held the grant; the registry's `>=` guard stays.

- **A strict-mode denial now names the file it denied, whatever characters the path contains** ([#164](https://github.com/Cohexa-ai/agent-coherence-plugin/issues/164)). Both deny texts were built with chained `replaceAll` / `replace` calls that passed the path as a replacement *string*, and a replacement string is not literal: `$&` inserts the matched placeholder, `$$` collapses to `$`, and `` $` `` / `$'` splice the surrounding template into the path. The chain also re-scanned what it had just inserted, so a path containing `{last_writer_short}`, `{last_writer_ts_iso}` or `{current_version}` took that value while the real placeholder shipped unexpanded. `docs/a$&b.md` was reported to the model as `docs/a{path}b.md`, a path it would then go and re-read. Both texts now render through the single-pass `fmt()` that SessionStart already used, which inserts each value once and never re-reads it, exactly as Python's `str.format` does; `fmt()` moves to `hook_payloads.ts` so both renderers share it. Only `permissionDecisionReason` was ever wrong: the decision, and the coordinator state after it, were unaffected. A test asserts Python's exact bytes for every affected token on both texts, with controls (`$1`, `routes/$id.tsx`, a path containing `{path}`) that already rendered correctly and must keep doing so; each text's half fails on its own when its old chain is restored.

- **Strict mode no longer lets a session write a file it was just refused a read of.** A strict-mode deny of a Bash or Grep read re-grants the session's read so that the retry the deny invites can run, and records nothing as read, because the denied command never ran. The strict check on `Edit` and `Write` looked only for a session the coordinator had invalidated, so that re-granted read also admitted the session's next edit: a whole-file `Write` from the copy it read before a peer's commit then overwrote the commit, with nothing denied after the shell read (Cohexa-ai/agent-coherence#275). An `Edit` or `Write` of a strict path is now denied while the session's last read of it is older than its current version; re-running the Bash command or reading the file with `Read` records the current version and lifts it (after a Grep deny only a `Read` does, because a Grep lists files rather than showing them). A session that has never read the file at all is still treated like a first-time editor. Pinned by two protocol-corpus fixtures the Python coordinator shares.

- **A Bash or Grep command denied in strict mode no longer counts as a read.** When `pre-bash` or `pre-grep` finds a stale tracked file, it re-grants the session SHARED. It does this in strict mode too: the deny fires once, and a retry goes through. That grant also recorded the file's current version as the session's `last_observed_version`, even though a denied command never runs. After a compaction, the re-grounding stale flag then stayed silent for a file the session had never read at its current version. The same false baseline would have made the grant-change denial described above tell a session that nothing had been written since "the version you last saw", a version it had been refused. The grant is now issued after the deny decision, and it records the observation only when the command will run. That holds for every file the command named, including warn-only ones in a denied command, and for a first-seen file registered by a denied command. The grant itself is unchanged. An allowed command still records the read, because it does read the current bytes. So does the retry the deny invites: a session that already holds the grant and reads the file again, through a retried Bash command or a Read, now has the current version recorded as seen. Without that, a strict session that recovered this way kept its baseline from before the deny, or none at all on a first touch, so a later grant handover was reported as a write it had already read and a first-touch file lost its post-compaction stale flag. A Grep is not credited for a file the session already holds: it names every tracked file under its root, not what it showed, so the baseline stays behind until a Read. `grantShared` is a no-op on a SHARED row, so the read is recorded by a new registry call, `recordObservation`, which moves only the baseline and only for a SHARED holder. The Python coordinator changes identically in `agent-coherence` releases after 0.14.1, and the protocol corpus pins both directions on both backends.

- **The admit-path preemption drain is bounded, so a pile-up no longer pushes `additionalContext` past what the platform delivers.** Every tracked-file admit hook drained an agent's entire pending-notice queue and rendered one bullet per notice, uncapped. On a workspace of this project's size that composed roughly **1.8x** the 10,000-byte ceiling -- and above that ceiling Claude Code does not truncate, it persists the prose to a file and hands the model a ~2KB preview plus a path, so the coherence notice becomes a pointer the model has to go and open. The bound is on the **consume**, not the render, which is the distinction a previous attempt ([#150](https://github.com/Cohexa-ai/agent-coherence-plugin/pull/150), closed unmerged) got wrong: `popPendingNoticesForAgent` now takes a `consumeLimit` that bounds the `DELETE` only, while the `SELECT` and the return value stay whole. The caller therefore renders the newest three, reports the **true** pending total in the intro, computes the overflow count as arithmetic on data it still holds, and leaves the remainder in the table -- which is what makes "still queued, they surface on your next tracked-file operation" a true sentence rather than the false one a render-only cap prints over rows it just deleted. This mirrors Python's `pop_pending_notices(consume_limit=)` exactly, including the value (3). The reasoning previously recorded in-source -- that a bound here needed a TTL sweep as a co-requisite -- was answering the render-cap design; a bounded consume drops nothing, so nothing needs reclaiming for correctness. The three near-identical inline drains in `pre_read`, `pre_edit` and `pre_bash`/`pre_grep` are now one helper in `hooks/_common.ts`, because three copies of a bound is three chances for one to drift. Measured end-to-end on `/hooks/pre-read` at 80 notices with 60-char paths: **11,037 to 2,022 bytes**, and the composed size is now independent of the notice count (2,076 B at 8 notices versus 2,022 B at 80). Cross-backend parity re-verified: the protocol corpus passes 61/61 against the bounded build. The bound holds on both axes: independent of the notice count, and still fitting at the longest path the policy admits (8,973 bytes at 80 notices with 1,020-character paths, against a `MAX_POLICY_PATH_LEN` of 1024). Getting the second axis required one more fix than the cap itself: the deferred re-grounding block is rebuilt at attach time, so once the drain stopped emptying the queue it began peeking the tail and rendering a SECOND notice block — whose intro reported the remaining count as though that were the number of grants revoked, handing the model two contradicting totals for one backlog and rendering rows the first block had just promised for next time. `buildSessionStartContext` now takes `includeNotices`, which the deferred seam passes false; the real `/hooks/session-start` endpoint is unchanged. That alone took the 800-character-path case from 10,216 bytes to 7,429. One property is worth knowing rather than fixing: because `nowTick()` floors to whole seconds, a burst of preemptions inside one second ties on timestamp and falls through to an `artifact_id` tiebreak over random UUIDs, so the cap now selects WHICH notices render rather than merely ordering them -- measured as five different rendered sets across five runs of one scenario. Nothing is lost and the choice is among simultaneous events, but it is why no `protocol_corpus` fixture pins this pile-up: a fixture asserts exact bytes and these are not stable across runs.

- **A failed provisioning install now reports what actually failed, instead of blaming your Node version.** When `npm install` fails, `bin/ensure-coordinator-node` prints a hint. Whatever had happened, it used to say that the `No prebuilt binaries found` / node-gyp trace above it "means this Node major lacks a better-sqlite3 prebuilt". That trace follows any failure to place the prebuilt binary, a dropped connection included, so a transient network error read as an unsupported Node version: on 2026-09-20 a CI install on Node 24, a supported major, failed this way and passed on a rerun. The install now runs npm at `--loglevel=http` so the prebuilt download's HTTP status is captured, and the hint names the cause it finds:
  - npm blocked an install script (`ESTRICTALLOWSCRIPTS`).
  - A 404: no prebuilt is published for this platform, architecture or libc, or a mirror or proxy answers 404 for the release host, so a retry is unlikely to help.
  - A 5xx or 429: transient, so retry.
  - Any other status, such as a proxy's 403: a refusal that a retry will not change.
  - A connection error such as `ECONNRESET`: your Node major is fine, and a retry is worth it.

  When it recognises none of these, it says so instead of guessing. npm's per-request lines at that log level are filtered out of what is printed, so a successful install shows the same output as before. The captured log is now also removed on the exit paths that used to leave it in `TMPDIR`.

- **A preemption notice could name a session that no longer held the grant.** `upsertPendingNotice` guarded its `ON CONFLICT DO UPDATE` with `WHERE excluded.preempted_at_unix_ts > pending_notices.preempted_at_unix_ts` — a strict `>` — while the same function's own docstring promised "latest preempter wins". Those disagree, because the timestamps are **whole seconds**: two preemptions of the same (victim, artifact) pair inside one second are indistinguishable by time, so the strict comparison declined the second and left the row naming the session it had already replaced. The model then read a bullet attributing the preemption to the wrong peer, which is the operator's only record of who took the grant. Reaching it requires the victim to re-arm a grant **without** draining its notice queue. When this was found, the strict-mode path did exactly that: `pre_bash` (and identically `pre_grep`) re-grants SHARED to suppress repeat fires, then returns the deny *before* `drainNoticeText`, and that reader was then queued a second notice. This was twice recorded on [#138](https://github.com/Cohexa-ai/agent-coherence-plugin/issues/138) as reachable only synthetically; it was reachable over the real hook surface. The fix for [#163](https://github.com/Cohexa-ai/agent-coherence-plugin/issues/163) in this release stops queueing notices for readers, which closes that path: the end-to-end test through `/hooks/pre-edit` → strict `/hooks/pre-bash` → `/hooks/pre-edit` → `/hooks/pre-read` now pins that the re-grant earns no second notice, and a registry-level test pins the state transition itself. The guard is now `>=`, which makes it last-write-wins within a second while still refusing a strictly **older** timestamp — the only ordering the comparison was ever load-bearing for, and itself pinned by a test. Python's `sqlite_registry` carries the identical strict `>` and correctly keeps it: the two backends feed that comparison different clocks. Node stamps `Math.floor(Date.now() / 1000)`, so two preemptions of one pair inside a second tie exactly and the strict form declines the second; Python is handed float `time.time()`, where two preemptions on separate requests do not collide. So there is no drift to reconcile and nothing to track — the tripwire is the clock, and it is recorded beside the guard itself in the library repo rather than in a ticket, because coarsening those timestamps is the change that would break it.

- **Warn-mode prose no longer promises a surface that cannot answer, and no longer spells timestamps in a dialect the Python coordinator never writes.** Three defects on the same model-visible surface. (1) When more preemption notices arrive than session-start renders verbatim, the overflow line reused the *artifact* template — "run `agent-coherence-status` for the full picture" — but `GET /status` carries `tracked_artifacts[].path/.version` and no notice data at any disclosure tier, so a coalesced notice pointed the model at an endpoint that cannot answer it. The notice block now has its own line saying the rows are still queued and surface on the next tracked-file operation, which is literally true because session-start reads the queue without removing anything from it. (2) `selectPendingNoticesForAgent` had no `ORDER BY`, so rows came back in `artifact_id` order — and artifact ids are random UUIDs, uncorrelated with preemption time. Harmless only while every caller drains and renders the whole queue; it now sorts newest-first like Python's `pop_pending_notices`, which is the prerequisite any bounded consume needs to delete the same set it rendered. (3) Every stale-read warning, edit-collision warning and preemption bullet formatted instants with `Date.toISOString()` (`…T12:00:00.000Z`) while the strict-deny path alone used the module's own `pythonIsoUtc`, which reproduces `datetime.isoformat()` (`…T12:00:00+00:00`) — so the highest-volume prose on the admit path byte-diverged from the canonical backend on every timestamp it printed. The cross-backend protocol corpus could not see this: its harness normalizes both spellings to the same `<TS>` placeholder. Verified instead by differential comparison against real Python across six instants (zero-fraction, `.5`, microsecond, `.999999`), byte-identical in every case.

### Security

- **The coordinator's YAML parser is updated to js-yaml 4.3.2, fixing a high-severity CPU-exhaustion advisory** ([GHSA-2883-xcg3-v3hh](https://github.com/advisories/GHSA-2883-xcg3-v3hh)). The Node coordinator parses `.coherence/tracked.yaml`, `ignored.yaml` and `strict_mode.yaml` with js-yaml, and those files can be committed to a repository you clone. In 4.3.1, merge keys with empty sources did not count toward the parser's merge limit, so a crafted policy file could keep the coordinator's only event loop busy. v0.5.0 locked 4.3.1; this release locks 4.3.2, and the first session after the upgrade reinstalls it.

- **The policy writer no longer follows a symlink planted at its temporary-file path** (CWE-59). `/policy/track` and `/policy/untrack` wrote the new policy to a fixed `.coherence/tracked.yaml.tmp` (or `ignored.yaml.tmp`) with a plain write, which follows a symlink, then renamed it over the policy file. A repository that committed that path as a symlink had the link's target overwritten with the policy contents on the next track or untrack, and the policy file itself replaced by the link. The writer now uses a per-write random name created exclusively (`O_CREAT|O_EXCL`), the pattern the caller-principal store already uses, and removes it if the rename fails. Present since the Node writer was introduced.

## [0.5.0] — 2026-08-25

**A compacted session no longer forgets what it held: the coordinator re-grounds it — grants at compaction, plus which artifacts peers moved — and provisioning survives Node major upgrades, script-blocked installs, and stale builds.**

### Added

- **Compaction-aware re-grounding.** When Claude Code compacts a session (auto or manual `/compact`), a second `SessionStart` hook entry now fires `hook-client session-start`, which gates on `source=compact` client-side and asks the coordinator's new `POST /hooks/session-start` endpoint for a re-grounding payload: the grants the session held at compaction (event-anchored prose) and each touched artifact's current coordinated version with a stale flag when a peer advanced it past the session's last-observed version (a new nullable `last_observed_version` column on `agent_states`, migration v4, recorded in-transaction at grant and commit time). The payload renders at the next user message and on `--resume`; a live autonomous loop additionally receives it on its next tool admit via a coordinator-side compact-pending flag claimed exactly once at the allow seam — strict-mode deny bodies stay byte-identical and never carry it. Payload prose is byte-identical to the Python coordinator's and pinned by six new protocol-corpus fixtures; capped at three artifact lines plus an overflow summary; empty sessions emit nothing. One benign residual duplicate is documented (mid-loop delivery followed by the next user turn's attachment render) and the closing self-qualifying line makes a second sighting harmless.
- **The release preflight now fails on a branch ruleset that forbids the documented release merge.** `main` is guarded by two independent systems — classic branch protection and the `protect-main` ruleset — which stack and are evaluated separately, and `tools/check_release_readiness.js` only ever inspected the first (plus the *tag* ruleset, a different object with different rules). The second drifted unseen into `allowed_merge_methods: ["squash"]` with `required_linear_history`, directly contradicting `docs/RELEASE.md` §2 step 2, which merges the release with a merge commit. v0.4.0 paid for it: the release was squash-merged, `main` was left with no ancestry link to `dev`, and the next forward-merge came back as add/add conflicts across every file the release touched, resolved by hand in [#112](https://github.com/Cohexa-ai/agent-coherence-plugin/pull/112). Preflight reported **0 failures** the whole time. A new check asserts that any active branch ruleset covering the default branch omits `required_linear_history`, includes `merge` in `allowed_merge_methods` (an absent list means all methods are permitted, and is accepted), and carries an admin bypass actor — without which `main`'s structurally unsatisfiable review requirement makes every release unmergeable. One visibility subtlety: `bypass_actors` is an admin-scoped field GitHub omits entirely for non-admin viewers — the release workflow's own `GITHUB_TOKEN` included — so from CI the bypass sub-check downgrades to a verify-locally warning instead of failing a correctly-configured release; the merge-method and linear-history sub-checks (whose fields are always visible) stay hard everywhere, and a *visible* bypass list without an admin actor still fails.

### Fixed

- **A Node major upgrade no longer kills the coordinator permanently.** Provisioning was keyed on a `diff` of `package.json`, which detects a *package* change but is blind to a *Node ABI* change — and native-module validity depends on `process.versions.modules`, which `package.json` cannot express. Provision under Node 23 (ABI 131), install Node 24 (ABI 137), and every session from then on crash-looped `The module '…/better_sqlite3.node' was compiled against a different Node.js version using NODE_MODULE_VERSION 131. This version of Node.js requires NODE_MODULE_VERSION 137.` with nothing to break the cycle. A package bump did not rescue it either: the 0.3.1 → 0.4.0 diff *did* fire, but `npm install` saw `better-sqlite3` already present at a satisfying version and skipped it, leaving the ABI-131 binary exactly where it was. `bin/ensure-coordinator-node` now stamps the provisioning ABI to `${CLAUDE_PLUGIN_DATA}/.node-abi` and treats a mismatch as an install trigger alongside the `package.json` diff, **tearing down `node_modules` before installing** so `prebuild-install` refetches the prebuilt for the running ABI (`npm rebuild` is deliberately not used — it compiles from source via node-gyp, and the plugin's zero-Python install path forbids a compile-time toolchain dependency). Trees provisioned before the stamp existed are probed rather than reinstalled, so upgrading costs a healthy install nothing and needs no network; and a `NODE_MODULE_VERSION` death at the post-spawn liveness gate invalidates the stamp, turning any remaining case of this failure into one bad session instead of a permanent one.
- **A silently script-blocked install is now caught at provision time instead of at first query.** `better-sqlite3`'s install script *is* `prebuild-install` — the prebuilt download itself — so an `ignore-scripts` in any npmrc yields a tree that installs "successfully" with no binary in it. Stage 1 now verifies the addon actually loads (constructing a `Database`, since `bindings` resolves the `.node` file lazily and a bare `require` succeeds against a missing binary) before stamping the ABI, and fails loudly with the likely cause rather than spawning into a crash loop. Relatedly, npm 11 gates install scripts behind an `allowScripts` allowlist: `package.json` now covers `better-sqlite3` explicitly, which both silences the default warning and keeps provisioning working for users whose npm config sets `strict-allow-scripts`. The zero-Python CI job and its install-time assertion run with that flag on, so any dependency that grows an install script fails CI until it is covered deliberately.
- **A plugin update that changes `src/` without bumping the version no longer serves a stale `dist/`.** Stage 2's rebuild key had the same shape as the ABI bug — `package.json` as a proxy for "the package changed" — so on the marketplace (dist-less) path the compiled output could outlive the sources it came from. The rebuild now also triggers when `src/` or `tsconfig.json` is newer than the built entry point.

## [0.3.0] — 2026-07-24

**Zero-Python Node coordinator + composite subagent identity.** The Node backend reaches full parity with Python — no Python install required for any surface, including strict mode — and subagents become first-class coherence peers via composite identity (SB-25).

### Added

- **Zero-Python Node coordinator.** The Node backend is now self-sufficient — a fresh install on a machine with no Python yields a complete working setup: all six hooks via a Node hook-client, the `track`/`untrack`/`status` CLIs, five previously Python-only routes (`/hooks/pre-bash`, `/hooks/pre-grep`, `/hooks/post-edit-cas`, `/policy/track`, `/policy/untrack`), and **strict mode** at byte-parity with Python. - **Composite subagent identity (SB-25).** A Claude Code subagent's hook payload carries the parent's `session_id`; the coordinator now folds the payload's `agent_id` into a composite identity so subagents are first-class coherence peers — correct attribution, sibling-collision detection, and a `SubagentStop`-scoped grant release. Absent/malformed `agent_id` resolves to the parent identity (an absent OR malformed id on subagent-stop is a no-op, never a parent-scoped release).

### Fixed

- **subagent-stop could release the parent's grants on a malformed `agent_id`.** A present-but-malformed `agent_id` passed the client's non-empty check, was nulled server-side, and degraded to a parent-scoped release. The client now shape-validates the id (both Node and Python) and the coordinator fails closed on a present-but-invalid id.
- **A subagent's own just-committed file was strict-denied as a "foreign edit."** The self-commit-lag suppression compared a derived session string against the parent `session_id`; it now compares the raw writer identity against the caller's composite agent id (both backends).
- **ReDoS in the Bash tracked-path detector.** The Node port had dropped Python's negative-lookbehind, so an adversarial dot-free command drove near-quadratic regex backtracking that blocked the single-threaded coordinator; the lookbehind is restored.
- **Unbounded `git` calls in coordinator discovery.** `findCoordinatorRoot` now bounds every `git` invocation with a 5s timeout (matching Python), preserving the always-exit-0 fail-open contract when `git` hangs.
- **`artifactNamesUnderPrefix` directory-boundary bug.** A bare prefix over-matched sibling directories (`docs/specs` → `docs/specs-internal/`) and returned nothing for a `.` search root (silently skipping the whole pre-grep stale check); it now mirrors Python's normalization (empty/`.`/`./` → all; trailing-slash boundary; exact-match UNION).
- **Policy-path validation gaps + wire divergence.** `/policy/track`/`untrack` now reject control characters (closing a YAML newline-injection vector), leading backslash, and over-long paths, with rejection reason strings byte-identical to Python (both now corpus-guarded).
- **Cross-runtime migration-ledger collision on the shared `state.db` ([#55](https://github.com/Cohexa-ai/agent-coherence-plugin/issues/55)).** The Node coordinator now fails closed when it opens a `state.db` written under the sibling Python coordinator's ledger, instead of running its own v3 migration on it (which added `agent_states.deadline_tick` and stamped `user_version=3`, after which the Python coordinator refused to reopen its own store). Detection mirrors the Python guard: a foreign `registry_meta.schema_runtime` stamp, the Python-only `artifact_versions` table, or the Python `artifacts.owner_generation` fence column raise a typed `CrossRuntimeSchemaError` (`reason = "cross_runtime_schema"`) before any migration runs. Node now stamps `registry_meta.schema_runtime = "node"` on create and back-fills it on migrate, so detection is symmetric from both sides. `user_version == 1` remains indistinguishable by design (the Node v1 schema mirrors Python v1 byte-for-byte).

### Changed

- **Removed destructive `rm state.db` recovery advice.** Now that the shared store holds durable retained version content and live coordination state, the schema-mismatch error, the v2 shape-mismatch error, and the README troubleshooting rows no longer advise deleting `state.db` / `.coherence/`; the secret-rotation step removes only `.coherence/hook.secret`.
